# 2 Phase Locking
- It is a type of pessimistic locking strategy that manages how transactions acquire and release locks in a database

## Phases
1. **Growing Phase (Phase 1):** In this phase, a transaction can only acquire new locks (both shared and exclusive) to perform its work. The number of locks can only increase, and no locks can be released
2. **Shrinking Phase (Phase 2):** Once a transaction releases its first lock, it enters this phase. Now, it can only release previously acquired locks and is strictly prohibited from acquiring any new ones

## Types of Two-Phase Locking
1. **Basic 2PL:** Follows the standard growing and shrinking phases where a transaction can release locks even before the transaction commits or ends
   - Drawbacks: It suffers from two major issues: Deadlocks and Cascading Aborts

2. **Conservative 2PL (Static 2PL):** Requires a transaction to acquire all of its necessary locks at the very start of the transaction before any execution begins. If any lock is unavailable, it must wait without holding partial locks
   - Pros & Cons: It completely prevents deadlocks because transactions never wait while holding locks
   - However, it is rarely used due to very low concurrency, extra overhead for the scheduler, and it does not prevent cascading aborts

3. **Strong Strict 2PL (Rigorous 2PL):** Transactions acquire locks gradually (Growing Phase) but hold all locks until the very end of the transaction (whether it commits or aborts) before releasing them

   - Pros & Cons: It completely avoids cascading aborts and is the most widely used approach in the industry
   - However, deadlocks are still possible


## Major Issues in 2PL
1. **Deadlocks:** This happens when two transactions wait indefinitely for each other to release locks. It can even happen on a single row if two transactions hold shared (read) locks and both attempt to upgrade to an exclusive (write) lock, causing them to block each other

2. **Cascading Aborts:** If a transaction updates a value, releases the lock early, but later aborts, any other transaction that read that uncommitted "dirty" value must also be aborted. This creates a chain reaction of failing transactions


## Deadlock Detection and Prevention Strategies
1. Timeouts: The scheduler assumes a deadlock if a transaction waits too long for a lock and aborts it. This can be flawed, as it might kill a perfectly valid transaction that is just taking a long time

2. Wait-For Graph (WFG): The scheduler maintains a directed graph of transactions waiting for each other. If a cycle forms in the graph, a deadlock is detected. The scheduler resolves this by picking a "victim" transaction to abort based on factors like effort already put in, time remaining, and the rollback cost. WFG is widely used with 2PL

3. Timestamp-Based Detection: Transactions are prioritized based on age; older transactions have higher priority. It uses two primary logics:
   - Wait and Die: Old transactions will wait for new ones to finish, but if a new transaction needs a lock held by an old one, the new transaction "dies" (aborts) instead of waiting
   - Wound Wait: Old transactions "wound" (abort) new transactions to take their locks, whereas new transactions must wait for old transactions to finish
