# Microservice Design Patterns

## Monolithic (Legacy)
- Overloads IDE
- Difficult to Scale
- Code fixing is difficult - 
- Every logic is tightly coupled

## Microservice
- Scaling is easy
- Cost effective
- Service are loosely coupled
- DISADVANTAGES
  - All services should be loosely coupled. Is services are not divided properly, they can have lots of communication between them (tightly coupled) and this can increase latency.
  - Monitoring becomes a bit difficult. If a service is being deployed it is important to see if its client doesnt break.
  - Transaction management. Every service may have its own DB. If a request comes which might need to make changes in DB over multiple service and in case it succeeds in one service and fails in another, it becomes difficult to rollback DB changes over other services
  
### Phases to divite into Microservice
  - Decomposition
    - Decompose by business logic
    - Decompose by sub domain
  - Database
    - DB per service
    - Shared DB
  - Communication
    - API
    - Event based 
  - Integration
    - API Gateways
  - Observability
    - Monitoring service

### Decomposition Pattern
- By business functionality/capability
- By subdomain (DDD)

#### Business Functionality
Example - Online order application can be divided into Order management, product management, account management, payment, billing, 

#### By Subdomain
Example - Each service above can be treated as a single domain and can be divided into service
Order Management domain can be divided into - order tracking, order placing
Payment domain can be divided into - forward payment, reverse payment
