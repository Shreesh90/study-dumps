# Strangler, SAGA and CQRS Patterns

# 1. Strangler Pattern
- Used when refactoring a monolithic to microservice
- Core concept is that we move the traffic to microservice slowly and gradually from monolithing service.
- Enables us to immediately revert back to legacy monolithic service in case anything breaks in in microservice structure

# Database Management in Microservice
- Shared Database
  - ISSUES
    1. If the requests for a single service is large in volume it leads to expansion of the whole DB
    2. If a single service wanted to delete a data from a table in DB, it will have to check the dependency of Data on all the other services. It has to make sure nothing else gets impacted.
  - Advantages
    1. Query Join is easy to do between different tables.
    2. Maintining Trasactional properties (ACID) - If any particular transaction fails, all the previous transactions can be easily rolled back.
- Databse for each individual Service
  - ISSUES
    1. Query join in tables across different DB in different service is difficult. **(Solved by CQRS)**
    2. If a transaction spans over different DB, its difficult to maintain ACID properties across all of them together. **(Solved by SAGA Pattern)**

# 2. SAGA Pattern (IMPORTANT)
- Choreography based SAGA
  - An event block received requests and services accepts the requests from event block and then sends another event upon completion
  - Other services listen from the event block and process
  - In case of failure, service publishes a failure event, which is picked up by other services to roll back the changes
  - DRAWBACK: A cycle dependency can get created
- Orchestration based SAGA
  - Orchestrator is a separate component which manages and calls separate services. 

# 3. CQRS Pattern
- Command (Create, Update, Delete)
- Query (Select)
- Request
- Seggregation

- All the updating transactions are dont in the service db itself
- Another DB (called view) is created used only for read, containing all the data from tables of indiidual services
- To keep View updates, we need to keep an event between the individual service DB and View. In any case of updation, the View listens to the event and also gets updated
